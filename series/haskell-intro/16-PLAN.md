## 記事の狙い

**ゴールは「組み立てと解釈の分離」**（決定事項 2）。

Free モナドの核心は [README.md](README.md) の「構想」に既に書いてある。

> **組み立て（Freeモナド側）と解釈（インタプリタ側）を分離するのが核心**。`>>=` は命令を
> つなげるだけで実行しない。できあがった手順書を辿って実際の処理に変換するインタプリタは
> 別関数として用意し、同じ手順書を本番実行用・テスト用モック・ログ収集用など複数の
> インタプリタで使い回せる。

15 回までのモナドは、`>>=` でつないだ時点で**意味が決まっていた**。
`IO` なら実行され、`Maybe` なら失敗が伝播し、`State` なら状態が流れる。
Free モナドは `>>=` に**何の意味も与えない**。ただ命令をデータとしてつなぐだけで、
意味づけはインタプリタに委ねる。ここが今までのモナドとの決定的な違いになる。

### この回の一行の主張

15 回の最後に自作した `Tree` が、そのまま Free モナドだった。

| 15 回の題材 | Free での表し方 |
|---|---|
| `data Tree a = Leaf a \| Node (Tree a) (Tree a)`（本文 `## Tree`）| `Free Two`（`data Two x = Two x x`）|
| `data Rose a = Leaf a \| Node [Rose a]`（練習【問4】）| `Free []` |
| `data Pair a = Pair a a`（練習【問1】【問2】）| 上の `Two` と同じ形 |

15 回はこれを**意図的に伏せてある**（15 回決定事項 9。先に言うと `Tree` が踏み台に見え、
自分で `>>=` を書く達成感が薄れるため）。**16 回はその回収から入る。**

> **枝の形が違うだけで `>>=` の中身は同じだった。その「枝の形」を型引数 `f` に
> くくり出したものが Free モナドである。**

`Tree` と `Rose` の `>>=` を並べると、違うのは枝を辿る部分（`Node l r` の左右を
再帰するか、`map` でリストを回すか）だけで、そこはちょうど `fmap` の仕事である。

```hs
Node l r >>= f = Node (l >>= f) (r >>= f)     -- Tree
Node ts  >>= f = Node (map (>>= f) ts)        -- Rose
Free g   >>= f = Free (fmap (>>= f) g)        -- Free
```

**Free モナドが `Functor` を要求する理由がここでそのまま出る。**
15 回の階層（`Functor` → `Applicative` → `Monad`）を経た直後の題材として噛み合う。

## 構成案

### 1. 木を一般化する（15 回の回収）

- **入口は 15 回の `Tree` と `Rose` の `>>=` を並べること。** 上記「一行の主張」の 3 行。
- 枝の形を型引数にくくり出す。

  ```hs
  data Two x = Two x x

  data Free f a = Pure a | Free (f (Free f a))
  ```

  - `Pure` が `Leaf`、`Free` が `Node` に対応する。
  - `Free Two Int` が `Tree Int` と同じ形であることを実際に値を組んで見せる。
  - `Free [] Int` が `Rose Int` に対応する。
- **`f` の種が `* -> *` であること**（14 回の種の回収）。`Free` 自体の種は `(* -> *) -> * -> *`。
  `:k Free` を GHCi で見せると効く。
- `instance` を書く。**15 回の定型（`fmap = liftM` / `(<*>) = ap`）がそのまま使える。**

  ```hs
  instance Functor f => Monad (Free f) where
      Pure a >>= k = k a
      Free g >>= k = Free (fmap (>>= k) g)
  ```

  - **`Functor f =>` という制約が付く理由**をここで説明する。枝を辿るのに `fmap` が要る。
    15 回で `Functor` を階層の一番下に置いた意味が、ここで実用の形で出る。
  - `instance` 側の制約は 14 回（`instance Show a => Show [a]`）で既習。
- ⚠ ここまでは「木の一般化」で閉じていて、まだ DSL の話は出さない。
  **`Tree` が Free だった、という驚きだけで 1 節を持たせる。**
- **末尾に練習【問1】**（`Free Two` で 15 回の `Tree` を組み直す）。
- ⚠ **`f` を差し替えると既知のモナドが出るという一覧表は作らない**（決定事項 11）。
  `Tree`・`Rose` の 2 つで閉じる。

### 2. 枝に意味を持たせる（DSL への転回）

**ここが記事の転回点。** 1 節では `f` を「枝の形」と呼んでいたが、
`f` を**命令の型**と読み替えると、Free モナドは命令の並びを表すデータになる。

- 題材は**ジェネレーター**（決定事項 7）。13 回で `Cont` を使って作ったものを
  Free で作り直す。**生産専用**（`yield` するだけ。13 回の本線と同じ範囲）。

  ```hs
  data GenF o next = Yield o next
  ```

- **`next` が「続き」であること**を強調する。`Yield` は値を 1 つ出した後の続きを持つ。
  → **13 回との接続はここ**（決定事項 14）。13 回は継続を `Cont` で捕まえたが、
  Free では続きがデータの中に直接入っている。**1〜2 段落 + 行末リンク**に留め、
  13 回を読んでいない読者にも分かるよう独立して説明する（README.md「スタイル」）。
- `instance Functor GenF` を手で書く。

  ```hs
  instance Functor (GenF o) where
      fmap f (Yield o next) = Yield o (f next)
  ```

  - **手で書いた後に `DeriveFunctor` を出す**（決定事項 6）。「構造から機械的に決まるので
    コンパイラに書かせられる」という 14 回の `deriving` の議論の続きになる。
    `{-# LANGUAGE #-}` の書き方自体は 06 回 `:217` で説明済みなので繰り返さない。
- **`liftF` で 1 命令を `Free` に持ち上げる。**

  ```hs
  liftF :: Functor f => f a -> Free f a
  liftF c = Free (fmap Pure c)
  ```

- スマートコンストラクタを定義して `do` で手順書が書けるようになる。

  ```hs
  type Gen o = Free (GenF o)

  yield :: o -> Gen o ()
  yield x = liftF (Yield x ())

  count = do
      yield 1
      yield 2
      yield 3
  ```

  - **この `count` はまだ何もしない**という点を強く言う。`do` で書いたのに実行されない。
    値は `Gen Int ()` という**データ**である。
  - 無限の手順書（`mapM_ yield [0 ..]`）も組める。組むだけなら止まらない。

### 3. インタプリタ（**この回の見せ場**）

- **本文は `toList` の 1 本**（決定事項 8）。手順書を辿って `Yield` の値を集める。

  ```hs
  toList :: Gen o a -> [o]
  toList (Pure _)           = []
  toList (Free (Yield o k)) = o : toList k
  ```

  - **13 回の `Cont` 版 `toList` と並べる。** あちらは継続を呼び出して駆動する必要が
    あったが、Free 版はデータを辿るだけの 2 行になる。
  - 無限の手順書に `take 5` が効くこと（遅延評価）。13 回の `nats` と同じ確認。
- **`>>=` が意味を持たないおかげで、意味を後から差し替えられる**ことを述べる。
  同じ `count` を `IO` で走らせるインタプリタも書けることを散文で示し、
  **実装は練習【問2】に回す**（決定事項 8）。
- ⚠ **ここで「これが `IO` と何が違うのか」に答える。**
  `IO` で書いたら実行するしかないが、Free なら中身を検査でき、モックにも差し替えられる。
  03 回・06 回の「アクションは実行される」との対比になる。
- **末尾に練習【問2】**（同じ手順書を走らせる `IO` 版インタプリタ）。

### 4. 「自由」とは何か

- **自由モノイドとの対比で説明する**（README.md「構想」に既述）。
  - リストは「モノイド則だけを満たし、それ以外の性質を持たない」構造。
    `[1] <> [2]` は `[1,2]` になるだけで、足し算にも掛け算にもならない。
    後から「どう畳むか」を `foldr` などで決められる。
  - Free モナドはこれのモナド版。**モナド則だけを満たし、それ以上の意味づけを持たない。**
    意味を後から決められるのは、意味を持っていないから。
- 14 回の `Monoid`・15 回のモナド則（`>=>` で単位元と結合法則に書き直した節）が
  そのまま足場になる。**「単位元と結合法則を持つ構造はモノイド」で締めた 15 回の続き。**
- **「自由生成（free construction）」という語を 1 行だけ出す**（決定事項 4）。
  由来の説明に留め、圏論の語は出さない。

### 5. テレタイプ DSL（~~練習【問3】【問4】~~ → **本文の解説**。変更点 13）

**ジェネレーター以外の DSL を読者に作らせる。** 独立した節にするか、
構成案 3 の後に練習として並べるだけにするかは執筆時に判断する。

⚠ **推敲で本文の解説に変更した。** 読者に作らせるのはスタックマシン（変更点 13）。
以下の記述は当初案として残す。

```hs
data TeletypeF next
    = PutLine String next
    | GetLine (String -> next)
```

- **`GetLine (String -> next)` が関数を持つ**のが `GenF` との違い。
  `fmap f (GetLine k) = GetLine (f . k)` と関数合成になる。
  ジェネレーターでは `next` が素の値だったので、ここで一段深くなる。
- 【問3】命令の型・`Functor`・スマートコンストラクタを書いて手順書を組む。
- 【問4】その手順書の**純粋インタプリタ（テスト用モック）**を書く。
  入力をリストで与え、出力をリストで集める。`IO` を使わずに振る舞いを検査できる。
  → **「テスト用モックが自然に書ける」という Free の実利を読者の手で作らせる。**
- ⚠ Brainfuck DSL 案は**不採用**（決定事項 9）。ループ命令の設計が重く、練習に向かない。

## free パッケージの扱い

**原理は定義を引用しながら説明し、実用ではパッケージを使う**（決定事項 5）。

- 本文では `data Free f a = Pure a | Free (f (Free f a))` と `liftF` の定義を示して
  仕組みを説明する。`instance` も自分で書いて見せる。
- その上で「実用では [free](https://hackage.haskell.org/package/free) パッケージを使う」と
  案内し、対応する API（`Free`・`liftF`・`foldFree`・`iterM` など）を対応表で示す。
- ⚠ **`free` はシステムの GHC には入っていない**（`ghc-pkg list` で確認。
  GHC 9.6.6 / mtl 2.3.1 / transformers 0.6.1.0 のみ）。**stack で導入して検証する**
  （決定事項 5）。cabal は環境に入っていない。
- ✅ **stack の共有ライブラリエラーは修復済み**（2026-08-07）。原因は pacman の部分アップグレードで
  `haskell-unicode-data` など haskell-* パッケージ群（189個）が `stack` パッケージより古いまま
  だったこと。`haskell-*` パッケージのみを対象に `pacman -S` で更新して解消した
  （`-Syu` は稼働中プロセスへの影響を避けるため見送った）。
- ✅ **執筆環境の resolver は `lts-22.28`。** システムの GHC（9.6.6）と一致するため
  `--system-ghc` が使える（`stack setup --system-ghc --resolver lts-22.28` で確認済み）。
- ✅ **記事の掲載コードに `stack script` ヘッダは書かない。実行コマンド側で
  `--resolver`・`--package` を指定する方式に決定**（2026-08-07）。理由は 2 つ。
  - ソースコードが素の Haskell のまま保てる（15 回までの掲載コードと見た目が揃う）。
  - 記事で「stack で動かす場合はこう起動する」という 1 行を示せば済み、
    導入手順の説明と掲載コードを分離できる。

  ```
  stack script --resolver lts-22.28 --package free ファイル名.hs
  ```

  - `stack runghc --package free -- ファイル名.hs` は本環境では `Setup.hs` の
    ビルドに失敗した（`Cabal`/`base` のパッケージDBが `--system-ghc` 併用時に
    壊れる模様）。**`stack script` の CLI 引数指定を使う。**
  - 記事に載せる resolver の値は執筆時点のものを使う（`lts-22.28` は 2026-08-07 時点の確認値。
    実際に記事を書く時点で最新 LTS を確認し直す）。
- ✅ **`free` パッケージの動作確認済み**（`check/16-free/test.hs`）。`Control.Monad.Free` の
  `Free`・`Pure` で `Two`（`Functor` を `deriving`）を使い 15 回の `Tree` 相当の木を組んで
  `toL` で走査し、`stack script --resolver lts-22.28 --package free test.hs` で
  `[1,2,3]` を得た（ソース側にヘッダは無し）。
- ⚠ パッケージ版の `Free` は本文で示す定義と**コンストラクタ名が同じ**（`Pure`・`Free`）
  だが、`Applicative` の実装など細部が異なる。差分は要調査（TODO）。

### 外部記事の棚卸し（2026-08-08）

日本語の Free モナド解説は 3 系統に分かれる。**どれとも入口が違う**ので、
シリーズの立ち位置は本文を変えなくても成立している。

|系統|例|特徴|
|---|---|---|
|ライブラリ利用・DSL 実践|[Freeモナドで領域特化言語を作るとプリティミューテーション](https://qiita.com/hiruberuto/items/3d55b0e54565dbb286a7)（Canvas API を DSL 化）・[Free Monadで言語内DSLをつくろう](https://lqtmirage.hatenablog.com/entry/2018/06/18/182130)|`free`／`purescript-free` 前提で定義は自作しない。自然変換など圏論語が断りなく出る。練習問題なし|
|自作実装・段階的シリーズ|[Freer Effectsが、だいたいわかった](https://qiita.com/YoshikuniJujo/items/988ac4b69a27974154fd)（全 N 回）|**最も本シリーズに近い。** 圏論用語を避けて自作する方針も同じ。ただしゴールが Freer Effects で、存在型・型族・GADTs まで登る|
|圏論|[自由モノイドとFreeモナド](https://hiratara.hatenadiary.jp/entry/20130525/1369495124)・[自由モノイド](https://bitterharvest.hatenablog.com/entry/2018/02/02/100008)|忘却関手の左随伴として「自由」を定義する。記号密度が高く前提知識が重い|

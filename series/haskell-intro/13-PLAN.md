## 記事の狙い

**bind は継続を抽象化したものである**という一点を伝える。
継続モナドは「難しいモナド」ではなく、これまでの回で書いてきた `>>=` の正体を
明示的に取り出したものだ、という位置付けにする。

その上で、応用としてコルーチンを実装して見せる。
「継続が値として取り出せると何が嬉しいか」を、実際に動くものの形で示す。

嬉しさが伝わる地点は**リストで素直に書けないところ**なので、生産専用のジェネレーターで
止めずに、双方向・IO 交互まで進む。ここが Zenn の単発記事との差分になる
（あちらは「型が循環する」現象とその解消が主題で、リストとの比較で終わっている）。

**本線はジェネレーター**とする。CPS で継続を取り出して何ができるかの例として最も素直で、
**値を相互にやり取りできればリストを超えられる**という形で「継続が値であること」の
必然性が出る。実用上は既存のジェネレーターやライブラリを使うべきだが、
本シリーズは**実用より原理の理解を優先**する方針なので、自分で組むところを見せる。

ただし実用を無視はしない。**リソース管理（`with` のネスト解消）は必要**なので、
原理を通した後に実用面の回収として置く（構成案 7）。

## 構成案

1. **bind と継続**
   - `m >>= k` の `k` は「残りの計算」＝継続である。
   - `do` ブロックが継続の連鎖に脱糖される様子を、既習のモナド（IO、Maybe、リスト）で確認する。
   - 継続が `>>=` の中に隠れていることを見せる。
2. **継続モナド** — **入口は `Identity` モナドからの地続き**
   - **CPS 変換を新しく教える必要はない。** 読者は 12 回分の `>>=` を既に知っており、
     `Identity` も既習（[10-monad-transformers.md](10-monad-transformers.md) の
     「Identityモナド」節。`09-state-monads.md` からも予告されている）。
   - 手順は 5 段階。
     1. 10 回の `Identity` を数行で再掲（既習なので定義の確認だけ）。
     2. その bind が**既に CPS** であることを指摘し、ここで CPS という語を与える。
        ```hs
        m >>= k = k (runIdentity m)   -- k を呼ぶだけ
        ```
     3. **`k` は外から来るだけで保持できない**という制約を示す。
     4. 保持する形に反転させると `(a -> r) -> r` になる。
        ```hs
        newtype Identity   a = Identity { runIdentity ::           a }
        newtype Cont     r a = Cont     { runCont     :: (a -> r) -> r }
        ```
     5. 増えたのは「継続を保持できること」だけ、と締める。
   - **`addK` のような CPS 変換の小例は落とす。** `Identity` の bind がその役を兼ねる。
     導出が「引き算」ではなく「反転」であることが重要で、器を引くだけでは
     `(a -> r) -> r` は出てこない（引いたら `Identity` に戻るだけ）。
   - 03 回（`cps-to-continuation`）が**同じ筋を JavaScript で辿っている**
     （`03-cps-to-continuation-monad.md:228-256`）ので、そちらへリンクする。
     核心の 1 文はこれ:
     > 恒等モナドに継続を渡すことはできますが、外部から与えられるだけで取り出すことは
     > できません。継続を取り出せるようにするため、モナド内部で継続渡しスタイルの関数を
     > 保持するようにしたのが**継続モナド**です。
   - 末尾再帰化の文脈（`cps-to-continuation` の 01・02 回）には深入りしない。
     あちらは「ループにするための CPS」、本記事は「継続を掴むための CPS」なので、
     動機が違う旨を一言添えてリンクで済ませる。
   - `return` / `>>=` / `evalCont` を実装する。
   - **「継続を保持できる」ことから 3 つの自由が出る。これが記事全体の見取り図になる。**

     | 得た自由 | 対応する内容 |
     |---|---|
     | `k` を呼ばない | `callCC` による早期脱出（構成案 3） |
     | `k` を後で呼ぶ | ジェネレーター（構成案 4・6） |
     | `k` を何度も呼ぶ | `GenClone` の分岐（6 (a) の後） |

   - 答えの型 `r` の役割を説明する（ここが後のコルーチンの伏線になる）。
     **`r` が何かという問いの答えの一つが「区切り」。** `evalCont` が prompt そのもので、
     その外の継続は捕まらない。ここは 1〜2 行で、限定継続という語はまだ出さなくてよい
     （**検証済み**: [check/13-cont-delimited/README.md](check/13-cont-delimited/README.md)）。
3. **callCC**
   - `callCC :: ((a -> Cont r b) -> Cont r a) -> Cont r a`
   - 早期脱出の例（`when (x == 0) (ret "zero")`）から入る。
   - 「現在の継続を引数として受け取る」の意味を、`\x -> Cont $ \_ -> c x` の実装から読み解く。
   - **`b` が多相なのは「呼んだら戻らない」ため**（abortive）。これは 6 (c) を落とす際にも、
     `Pipe` で脱出継続を多相に付け直す小細工の根拠にもなっていた性質。
   - **末尾で限定継続に触れる**（数行）。
     - `callCC` は abortive、`shift` は composable。`callCC` の `k :: a -> Cont r b` は
       `b` が多相＝戻らないので `x <- k 1` の後に到達しない。`shift` の `k` は値を返すので
       `reset (1 + shift (\k -> k (k 3)))` = `5` が書ける。
     - `reset`/`shift` は自作不要で `Control.Monad.Trans.Cont` に入っている。
     - **`shift`/`reset` の意味は簡潔に自前で説明する**（`reset` が区切りを作り、
       `shift` がその区切りまでの継続を値として捕まえる。捕まえた `k` は関数として
       何度でも呼べ、呼んだ結果を合成できる）。詳しい意味論の解説は Scheme の
       [限定継続でジェネレーターを実装する](https://qiita.com/7shi/items/6db3e19ddc1f8552d9a0)へ
       譲るが、ここで最低限の理解は完結させる（決定事項 5 の変更）。
     - 締めは「**`callCC` は区切りの中の undelimited な call/cc**」。
     - **03 回はこの話を 2 回「機会を改めます」と先送りしている**
       （`03-cps-to-continuation-monad.md:360, 489`）。回収先はここしかない。
4. **応用: コルーチン**
   - 継続を返して抜け、後で再開する ＝ ジェネレーター。
   - 答えの型 `r` を自分自身にする必要があること、そこで型が循環すること。
   - **`data` で包んで解決する。** ここが記事の山場。
   - **`type` は展開されるだけなので再帰できないが、`data`/`newtype` は名前が型として
     自立するので再帰できる**、という対比をここで説明する（決定事項 7）。
     `occurs check`・無限の型という語もここが初出になる。
     02 回の[型シノニムの節](02-algebraic-data-types.md)へはこちらからリンクする。
   - 有限・無限の両方の例を出し、`mapM_` など既存のコンビネーターがそのまま使えることを見せる。
     （**構成案 7 の `forM` と対になる。**「モナドにすると既存のコンビネーターが効く」が
     本線と実用で 2 回鳴る構図。）
5. **リストとの境界**
   - ここまでの使用例はすべて遅延リストで書ける。
     `[1,2,3]` / `[0 ..]` / `map (^ 2) [1 .. 5]`、一般の状態機械は `unfoldr`
     （`Just (値, 次の状態)` が `yield` に相当）。
   - 遅延評価は「消費されるまで計算しない」ので、`toList` で取り出す形の
     ジェネレーターと役割が重なる。`toList` で `Gen a` → `[a]` に変換できたのは、
     4 のジェネレーターが**生産する側だけ**のコルーチンだったから。
   - ここで止めると「リストで十分」で終わってしまうので、**次へ進むための線引き**として置く。
   - **線引きの言い方に注意**（決定事項 1）。「リストでは書けない」と言い切ってはいけない。
     6 (a) の双方向ジェネレーターはリスト関数に潰せるし、6 (b) すら
     遅延リストの knot-tying でなら書ける。正しい線引きは
     **「リストでも書けるが、遅延に頼った knot-tying が要り、Haskell はそれを試して捨てた」**。
     この形にすると、5 の問いの答えが思弁ではなく**史実**になる（6 (a) 末尾で回収する）。
6. **リストで素直に書けないものを実装する**（本記事独自の見せ場）
   - **(a) 双方向のやり取り** — 再開時に値を渡す（JS の `it.next(x)` に相当）。
     出力の型と入力の型を分ける。`yield` の戻り値が、次の再開時に渡された値になる。
     ```hs
     data Gen i o = Done | Yield o (i -> Cont (Gen i o) (Gen i o))
     ```
     **この型のまま通ることを検証済み**（型の循環は再発しない。`RankNTypes` も不要）。
     捕まえた継続 `next` は関数なので引数を渡せる、という 3 の `callCC` の話が効く。
     題材は累算器（渡した値を足し込んで途中結果を `yield` する）程度で十分。
   - **生産専用版からの差分は `(next ())` → `next` だけ。** ここが最大の見せ場。
     ```hs
     yield ccOut v = callCC $ \next -> ccOut (Yield v (next ()))  -- 生産専用
     yield ccOut v = callCC $ \next -> ccOut (Yield v  next    )  -- 双方向
     ```
     生産専用版は捕まえた継続に `()` を渡して潰していただけで、渡さずそのまま
     格納すれば双方向になる。「継続は関数である」が差分そのものとして目に見える。
     `yield` の型が `GenM i o ()` → `GenM i o i` に変わり、脱出継続の答えの型も
     連動して `()` → `i` になる（`callCC` の型から追える）。
   - **`toList` が書けなくなり、`feed :: Gen i o -> [i] -> [o]` になる。**
     生産専用版で `toList` が書けたのは入力が `()` に潰れていたからだと振り返れる。
   - ⚠ **`feed` を「リストを超えた証拠」として使ってはいけない**（決定事項 1）。
     `feed` の型は `[i] -> [o]`、すなわちリストからリストへの関数で、`accum` の例は
     `scanl` そのもの。`feed` が示すのは逆に、
     **入力を先に全部与えるなら双方向コルーチンはリスト関数に潰せる**ということ。
     → **その潰した姿が Haskell 1.0 の `type Behaviour = [Response] -> [Request]`。**
   - 実行結果を載せるときの注意: ジェネレーターは「まず出して、それから受け取る」ので
     入出力の個数がずれる。`accum` に `[1,2,3,4]` を渡すと `[0,1,3,6]` で、
     `6+4=10` は出ない。一言説明しないと読者が数え違える。
   - 検証コード・確認内容: [check/13-gen-bidirectional/README.md](check/13-gen-bidirectional/README.md)
     （標準の `Cont` 版と全部自前の最小実装版の両方。コルーチン部分は `diff` で同一）
   - **(a) の末尾に 3 つ置く。**
     1. **歴史の要点**（決定事項 2、下の「Haskell 1.0 の I/O」節）。数行＋リンク。
        `feed prog` の型が `Behaviour` に一致するので、**今書いたものが Haskell 1.0 だった**
        と落とせる。5 の「リストで十分では」への史実による回答にもなる。
     2. **`shift` 版との比較**（決定事項 5）。構成案 3 末尾で説明した `shift`/`reset` を
        使ってジェネレーターを書き直し、`ccOut` の引き回しが消えることを実際のコードで示す。
        読者が確実に持つ疑問への回答（検証: [check/13-cont-delimited/README.md](check/13-cont-delimited/README.md)
        の `Shift.hs` 節、コードは `Shift.hs` そのもの）。Scheme 記事へのリンクは
        「意味論のより詳しい解説」として添える。

## Haskell 1.0 の I/O（歴史的補足）

**IO モナド導入前の Haskell は遅延ストリームで副作用を扱っていた。**
この記事の「リスト vs 継続」という対立軸は、Haskell が実際に通った道そのもの。

**歴史そのものは単発記事へ分離した。本編では深入りせず要点だけ参照する。**

- 記事: [Haskell の IO モナドへの道](https://zenn.dev/7shi/articles/20260731-haskell-io-history)（Zenn）
- 検証コード: zenn リポジトリ `check/20260731-haskell-io-history/`

典拠は Hudak, Hughes, Peyton Jones, Wadler,
[*A History of Haskell: Being Lazy with Class*](https://www.microsoft.com/en-us/research/publication/a-history-of-haskell-being-lazy-with-class/)
(HOPL III, 2007) の 7 節。詳細は分離した記事にあるので、以下は本編で使う分だけ残す。

### 前提となる事実（詳細は分離記事）

- Haskell 1.0 (1990) はストリーム版と継続版の I/O を両方載せていた。
  ストリームを primitive、継続をその上の派生とした（理由は効率）。
  モナド版は Haskell 1.3 (1996) で両者を置き換えた。
- プログラムの型は `type Behaviour = [Response] -> [Request]`。
  順序の正しさは遅延パターン `~` で守るしかなかった。

### 本編にとっての価値（検証で分かったこと）

1. **双方向ジェネレーターは `Behaviour` そのもの。** 構成案 6 (a) の
   `feed prog :: [Response] -> [Request]` が型として `Behaviour` に一致する。
   Figure 3 のプログラムをコルーチンとして書いて Haskell 1.0 の OS に差したら動いた。
   `[Response] -> [Request]` は**双方向コルーチンを 2 本の遅延リストで表したもの**だった。
   → **`feed` が書けてしまう理由の答えがこれ**（決定事項 1）。
2. **答えの型 `r` の具体例が歴史上にある。** Haskell 1.0 の継続 I/O では
   `readFile name abort :: (String -> Behaviour) -> Behaviour` で、これは
   `Cont Behaviour String` そのもの。`r` が「これから OS に出す要求の列」という
   具体物だった。構成案 2 で「`r` は抽象的で掴みにくい」と言った後の実例になる。
   実際に `Cont` で包んで `do` 記法にしたら Figure 6（モナド版）と同形になった。
3. **`~`（遅延パターン）の必要性が、こちらの落とし穴と同じもの。**
   `~` を外すと Figure 3 はデッドロックする。そして `13-gen-bidirectional` の
   `feed`（入力を先にパターンマッチする版）を knot-tying で使うと**同じくデッドロックした**。
   出力を先に出す形に直すと通る。つまり `~` でやっていた配慮が、コルーチンでは
   ドライバー側に移り、プログラム本体では意識せずに済む。
   `13-gen-io` の「素朴な `take` が 1 つ余分に生産する」も同じ型の同期のずれ。
   **純粋なら遅延が吸収するが、副作用が付くと露出する**という一点に集約される。
   → **構成案 5 の線引き（「リストでも knot-tying なら書ける」）の根拠がこれ。**

### 構成上の扱い

- **置き場所は 6 (a) の末尾**（決定事項 2）。`feed` を書いた直後に
  「この型は Haskell 1.0 のプログラムの型そのものだった」と落とす。
- **分量は数行に抑え、詳細は分離記事へのリンクで済ませる。**
  `Behaviour` の型と「`~` が必要だった」「継続版もあった」の 3 点程度。
  Figure 3・4 を載せる必要はない（分離記事にある）。
- 記事全体の狙い（**bind は継続を抽象化したもの**）とも噛み合う。論文が
  「Haskell を命令型っぽく見せたのはモナドそれ自体ではなく `do` 記法の登場だった」
  と書いており、構成案 1 の「`do` は継続の連鎖に脱糖される」と直結する。

## 限定継続との関係

**「継続モナドは真のコールスタックをいじらないので、限定継続では？」への答え。**
**検証済み**: [check/13-cont-delimited/README.md](check/13-cont-delimited/README.md)

争点を 2 つに分けると整理できる。**到達範囲としては限定的だが、`shift`/`reset` とは別物。**

1. **捕まえた継続は first class**（ここは限定的ではない）。ただの関数値なので
   データ構造に格納でき、`evalCont` が返った後でも、何度でも呼べる（`GenClone.hs`）。
   **「コールスタックをいじらない」ことは first class 性を損なう理由ではなく、
   成り立たせている理由。** Scheme のネイティブ `call/cc` がスタックのコピーで達成する
   multi-shot を、CPS では継続がクロージャなのでタダで得ている。
2. **到達範囲は `evalCont` まで**（ここは限定的）。脱出しても `evalCont` の外は実行される。
   **答えの型 `r` が区切り（prompt）の正体**と言える。
3. **`callCC` は abortive、`shift` は composable。** ここが決定的な差。
   `callCC` の `k :: a -> Cont r b` は `b` が多相＝戻らないので、`x <- k 1` の後は
   到達しない。`shift` の `k` は値を返すので `k (k 3)` や `k 10 + k 20` が書ける
   （`reset (1 + shift (\k -> k (k 3)))` = `5` がそのまま動く）。
   `reset`/`shift` は自作不要で `Control.Monad.Trans.Cont` に入っている。

→ **`callCC` は「区切りの中の undelimited な call/cc」。**
「セマンティクスとしては限定継続」は、到達範囲の話としては正しく、
継続の性質の話としてはミスリード。

### `shift` 版のジェネレーターが書けてしまう問題

Scheme の[限定継続でジェネレーターを実装する](https://qiita.com/7shi/items/6db3e19ddc1f8552d9a0)は
`call/cc` 版と限定継続版を並べ、限定継続版の方が簡単だと結論している。
**これは Haskell でもそのまま再現する**（`check/13-cont-delimited/Shift.hs`）。

```hs
-- callCC 版: 脱出継続 ccOut を引き回す
yield ccOut v = callCC $ \next -> ccOut (Yield v next)

-- shift 版: ccOut が消え、Out 型ごと不要になる
yield v = shift $ \k -> return (Yield v (return . k))
```

**本線は `callCC` のままとする**（決定事項 5）。理由は 3 つ。

1. 記事の狙いは「bind は継続を抽象化したもの」で、`callCC` は `Cont` の定義から直接出る。
   `shift`/`reset` はもう一段の抽象で、区切りという別概念が要る。
2. `(next ())` → `next` という 6 (a) の見せ場は `callCC` 版の方が鮮明。
3. 03 回も `callCC` で書いており、シリーズの連続性がある。

ただし Scheme の 2 部シリーズを読んだ読者は必ず疑問に思うので、**黙殺はしない**。
また Scheme 記事はネイティブ `call/cc` 前提の意味論なので、Haskell の CPS
エンコーディングとは継続の扱いが違い、リンクだけでは丸投げになる。
**6 (a) の末尾で `shift`/`reset` を自前で説明した上でコードを書き直して見せる**
（決定事項 5 の変更）。

### 構成上の扱い（3 箇所に分ける）

- **構成案 2「答えの型 `r` の役割」** — 「`r` は区切りである」を 1〜2 行。
  「`r` は抽象的で掴みにくい」への回答になる。限定継続という語はまだ出さなくてよい。
- **構成案 3 の末尾** — abortive vs composable を数行。`shift`/`reset` の意味
  （`reset` が区切りを作り、`shift` がそこまでの継続を値として捕まえる）を
  簡潔に自前で説明する。Scheme 2 部シリーズと 03 回へは「より詳しい解説」として
  リンクする。
- **構成案 6 (a) の末尾** — `Shift.hs` を使ってジェネレーターを書き直し、
  `ccOut` の引き回しが消える様子をコードで示す。

## 他言語との対応

**⚠ 決定事項 3: 「対応」節も対応表も作らない。async/await には触れない。**

他言語の材料はほぼ全部**既存の 2 記事が既に持っている**ので、本編は言及せずリンクで足りる。

- Node のコールバック = Haskell 1.0 の 2 継続、callback hell = Figure 4 の括弧の山
  → **Zenn の歴史記事**にある（他言語の類似実装に言及済み）
- コールバック → Promise → async/await → `co`（ジェネレーター版）
  → **[非同期APIをPromiseでラップしてasync/awaitで使う](https://qiita.com/7shi/items/a2bb35f27cd4a56f7bac)**
  （`articles/javascript/wrap-async-api-with-promise.md`, 2020）が覆っている。
  コールバックを CPS と呼び、`resolve` が継続に近いことにも触れ、まとめでは
  「コールバックから async/await への書き換えは、Haskell での `>>=` を明示した書き方から
  do ブロックへの書き換えに対応します」と書いて本シリーズ 05 回にリンクしている。

**捨てるのは「6 (a) + (b) を組み合わせたものが async/await だった」の 1 点だけ。**
強い対応ではあったが、`co`/regenerator のドライバーを説明しないと成立せず、
Haskell シリーズの軸から最も遠いので代償は小さい。

`check/13-js-async/README.md` で確認した内容は、対応関係の裏取りとして持っておくだけでよい。

### 本編に残す 2 つ

1. **既存のジェネレーターより能力が上**（6 (a) の末尾。**本記事オリジナルの主張はここだけ**）

   **`Gen i o` は純粋な値なので、同じ中断点から何度でも再開できる**（検証済み、
   `check/13-gen-bidirectional/GenClone.hs`）。違う入力で再開すれば分岐して木になる。

   ```hs
   let g = step accum 10
   peek (step g 1)     -- Just 11
   peek (step g 100)   -- Just 110   ← g は消費されない
   ```

   JavaScript / Python のジェネレーターはこれができない（だから
   [イテレーターのクローンもどき](https://qiita.com/7shi/items/6575cbb98c5a710a2945)が
   最初からやり直す回避策を書いている）。Promise も `resolve` を 2 回呼べない
   （2020 年の記事が相違点として挙げている）。

   → **「実用には既存のジェネレーターを使えばよいのでは」への答えになる。**
   原理を理解するために自前で組む、という方針に加えて、**自前版の方が能力が上**という
   実利まで言える。`callCC` の「継続は何度でも呼べる」がそのまま機能として出ている点で、
   構成案 2 の 3 つの自由・構成案 3 の回収にもなる。

2. **Python の `with` はジェネレーターで実装できる**（`@contextmanager`。構成案 7 の導入）

   `yield` の位置で `with` の本体（＝継続）が走る。手で駆動すると `with_` が `runContT`、
   `body` が継続だと露わになる。出力は `13-cont-resource/Order.hs` と完全に一致した。
   → **構成案 6（コルーチン）と 7（リソース管理）は別の応用ではなく同じ仕組み。**
   7 を「おまけの実用例」ではなく**本線の言い換え**として位置付け直せる。

## 今回は入れなかった話（今後の回へ）

**「bind はそもそも CPS である」の裏付けとなる普遍性の話。13 回には入れない。**

13 回では「`>>=` の型がもともと継続渡しの形をしている」ところまでを本文に入れた
（`# 継続モナド` 冒頭の「順序に注意してください」の段落）。
なお `## bind と CPS` に `>>=` の型を明示する案もあったが、散文で足りるので入れなかった。
その先の「なぜそうなっているのか」を裏付ける材料が以下の 3 つだが、
**超入門の射程を超えるので置かない。** 後続の回で拾う。

1. **論理としての普遍性** — `(a -> r) -> r` は二重否定 `¬¬a` に対応し、CPS 変換は
   Kolmogorov の二重否定変換と同じ形。`callCC :: ((a -> b) -> a) -> a` はパース則に
   対応し、古典論理と直観主義論理の差がちょうど継続に対応する。
   → 構成案 3 の abortive の説明の直後に ※ 1〜2 行で入れることは可能だが、
   カリー・ハワード対応がシリーズ未出なので前置きが要る。**保留。**
2. **表現力としての普遍性** — Filinski, *Representing Monads* (POPL 1994)。
   第一級の継続と状態があれば任意のモナドをシミュレートできる。`State` も `Maybe` も
   `List` も、答えの型 `r` を選べば継続の上に載る。
   → **「なぜ継続モナドは他のモナドとうまく噛み合うのか」への直接の答え。**
   置き場所は「モナドとゆかいな仲間たち」が自然。
3. **圏論としての普遍性** — `forall r. (a -> m r) -> m r` は codensity モナドで、
   任意のモナドをここに埋め込める。Church エンコードした free モナドや `DList` が速いのは、
   この埋め込みで bind の左結合を右結合に潰しているから。
   → **Free モナドの回の高速化の話と直結する**ので、置くならそちら。

置き場所の候補は「型クラス 超入門」ではなく、**「モナドとゆかいな仲間たち」（2 が本命）**と
**「Free モナド 超入門」（3 が本命）**。1 はどちらにも入れられるが、無理には入れない。

## 記事の狙い

**ゴールは「ad hoc 多相」という考え方**（決定事項 1）。

型クラスは **ad hoc 多相**（型ごとに違う実装が選ばれる多相）を実現する仕組みである、
という一点に記事を集約する。読者は 13 回分ずっと型クラスを**使って**きたが、
その仕組みを説明されたことがない。`deriving Show`・`Monad m =>`・`return` はすべて
型クラスの上に載っているのに、シリーズはその都度
「今回の範囲を超えるため省略します」で通り過ぎてきた。14 回はその回収であり、
**未回収の予告がシリーズ最多の回**でもある。

対比の軸は**パラメトリック多相**（決定事項 3）。

| | 実装 | 例 |
|---|---|---|
| パラメトリック多相 | すべての型で**同じ**実装 | `id :: a -> a`, `length :: [a] -> Int` |
| ad hoc 多相 | 型ごとに**違う**実装 | `show :: Show a => a -> String` |

型変数そのものはシリーズで説明済みなので、**制約が付くかどうかが両者を分ける**という
形で対比を立てられる。`a =>` が付いた瞬間に何が変わるのかが記事の主題になる。

強調すべき核心は、オブジェクト指向のインターフェースとの違い。

- OO のインターフェースは**値**（レシーバ）が実装を決める。
- 型クラスは**型**が実装を決める。値がなくてもよいので、
  **戻り値の型だけで実装が選べる**（`read`・`mempty`・`minBound`・`return`）。

この違いが「なぜ `read s` は `:: Int` を付けないと決まらないのか」
「なぜ `return 1` はどのモナドにもなれるのか」という、
読者がシリーズ中ずっと不思議に思ってきたはずの現象の答えになる。
そして**辞書渡し**（構成案 9）が、その両方に共通する理由を与える。

## 構成案

### 1. 2 種類の多相

- **冒頭で ad hoc 多相とパラメトリック多相を対比し、記事の見取り図にする**（決定事項 3）。
  - パラメトリック多相: `id :: a -> a`、`length :: [a] -> Int`。
    型変数はシリーズで既習なので復習として短く。
    **型が何であっても中身は同じ**なので、実装は 1 つで足りる。
  - ad hoc 多相: `show :: Show a => a -> String`。
    `Int` と `Bool` では表示の仕方が違うので、**実装が型ごとに要る**。
  - 分かれ目は `=>`（型クラス制約）が付くかどうか。
- ここで既習事項を棚卸しする。`deriving Show`（02 回）・`Monad m =>`（07 回）・
  `return`（06 回以降）は、すべて ad hoc 多相の仕組みの上に載っている。
- 「その仕組みが型クラスであり、今回はそれを自分で定義する」と宣言して次へ。
- **末尾のまとめで改めてこの対比に戻る**（予告 → 回収）。

### 2. class と instance（入口はオーバーロード）

**02 回の宿題を直接回収する**（決定事項 4）。02 回は「型クラスの定義は今回の範囲を
超えます」と書いて [Haskellで関数のオーバーロード](https://qiita.com/7shi/items/17a1567a635af17fc83f)
へ逃がしているので、**その続きとして入る**のが最も筋が通る。
「同じ名前で型ごとに違う実装を選ぶ」は ad hoc 多相の定義そのものなので、
構成案 1 のゴールとも直結する。

- 02 回の Java の例（`foo(int)` / `foo(String)` のオーバーロード、`02:326-366`）を
  1 つ引き直し、「Haskell ではこう書く」と型クラスで書く。

  ```hs
  class Foo a where
      foo :: a -> String

  instance Foo Int where
      foo 1 = "bar"
      foo _ = "?"

  instance Foo Bool where
      foo True  = "baz"
      foo False = "?"
  ```

- `class` は**宣言**（型と名前だけ）、`instance` は**実装**という対比を明示する。
- **メソッドという語をここで与える。** 12 回の引用ツイート（`:1584`）で
  「`Alternative` 型クラスのメソッド」という言い方が既に出ている。
- 自作型でも同じことをする（02 回の `Color` を再利用すると連続性が出る）。
- ⚠ `instance Foo String` は `FlexibleInstances` が要る（`String = [Char]` は型シノニム）。
  **超入門では拡張を出さないため、題材の型は `Int`・`Bool`・自作型に留める。**
  既存記事がこの拡張の話をしているので、踏み込みたい読者はそちらへ誘導する。
- ⚠ 既存記事と題材が重なるが、**他言語（C++・Java・F#）との比較はあちらに譲り、
  こちらは Haskell 側の仕組みに集中する**ことで棲み分ける。

### 3. デフォルト実装

- `class` 本体に実装を書いておくと `instance` 側で省略できる。
- 題材は `Eq`。`==` を定義すれば `/=` が付いてくる（逆も可）。

  ```hs
  class Eq a where
      (==), (/=) :: a -> a -> Bool
      x == y = not (x /= y)
      x /= y = not (x == y)
  ```

- **最小完全定義**（minimal complete definition）という語をここで与える。
  GHCi の `:info Eq` で見えることも書いておくと実用的。

### 4. 型クラス制約（定義する側から見直す）

- 07 回で「使う側」は説明済みなので、**ここでは制約が何を要求しているかを説明し直す**。
  `f :: Eq a => a -> a -> String` の `Eq a =>` は
  「`a` に `==` の実装があること」を要求している。
  （この「要求」が実体として何なのかは構成案 9 の辞書渡しで答える。）
- 複数の制約 `(Eq a, Show a) =>`。
- `instance` 側の制約 `instance Show a => Show [a]`。
  **02 回以降ずっと `print [1,2,3]` が動いていた理由がこれ**で、
  インスタンスが再帰的に組み立てられることが見える。良い題材。

### 5. 戻り値の型で実装が選ばれる（**この回の山場**）

- **OO のインターフェースとの決定的な違い。** メソッドの引数に `a` が現れなくてもよい。

  ```hs
  read     :: Read a  => String -> a
  return   :: Monad m => a -> m a
  mempty   :: Monoid a => a          -- 引数に a が無い
  minBound :: Bounded a => a
  ```

- 02 回の表で挙げながら例を省いた `Read`・`Bounded` の回収がここでできる（`:180`）。
- `read "123" :: Int` と書かないと決まらない理由。
  `print (read "123")` が **ambiguous type variable** で落ちること。
  **読者が必ず踏むエラーなので、実際のエラーメッセージを載せる**（TODO で採取）。
- `return 1` が `IO`・`[]`・`Maybe`・`Cont` のどれにもなれた理由（06〜13 回の回収）。
  - ⚠ `pure` との関係には触れない（決定事項 6）。`return` の型だけで話を閉じる。
- **型のデフォルト規則にも一言触れる。** `print 1` が動くのは `Num` の
  デフォルトが `Integer` に決まるため。「なぜ数値リテラルだけは注釈が要らないのか」は
  自然に湧く疑問なので、1〜2 行で答えておく。規則そのものは深追いしない。
- **F# のインターフェースとの比較記事へリンクする**
  （[Haskellの型クラスとF#のインターフェース](https://qiita.com/7shi/items/cd7f65a898dd5696c73d)）。
  あちらの「似ているのは定義だけで、実装や呼び出し方法はあまり似ていません」という結論が
  本節の主張と一致する。

### 6. スーパークラス（型クラスの継承）

- `class Eq a => Ord a` — `Ord` のインスタンスは `Eq` のインスタンスでもある。
  02 回で `deriving (Eq, Ord, ...)` と並べて書いていたものに順序関係があったと分かる。
- **`Semigroup` → `Monoid` を主題材にして 09 回の `Writer` を回収する**（決定事項 5）。
  - `tell` がリストへの追記だったのは `Monoid` の `<>`・`mempty` を使っていたから。
  - `Writer` の型クラス制約 `Monoid w =>` をここで開いて見せる。
  - **`mempty` は構成案 5 の「引数に `a` が無い」例そのもの**なので、
    5 と 6 が同じ題材で繋がる。一石二鳥。
  - `Semigroup` が `Monoid` のスーパークラスであることは
    「`<>` だけ持つ段階」と「単位元 `mempty` も持つ段階」という積み上げとして説明できる。
- ⚠ `Functor` → `Applicative` → `Monad` の階層は**扱わない**（決定事項 6）。
  スーパークラスの例としては `Eq`/`Ord` と `Semigroup`/`Monoid` で足りる。

### 7. 型引数を取る型クラスと種（kind）

**語を与えて `:k` まで見せる**（決定事項 7）。

- ここまでの型クラスは `Int`・`Bool` のような**型**に対するものだったが、
  `Monad` は `IO`・`[]`・`Maybe` のような**型を取って型を返すもの**に対して付く。
- 07 回の記述（`:236`）がそのまま足場になる。

  ```hs
  a ::            IO Int
  b ::            [] Int
  c :: Monad m => m  Int
  ```

- 「型の型」として**種**（kind）という語を与え、GHCi の `:k` で確認する。
  `Int` と `Maybe` を並べると差が見える。
- ⚠ GHC 9.6 の `:k` が `*` と `Type` のどちらで表示するかは **要確認**（TODO）。
  → **`*` だった。**記事もこれに合わせた。`check/14-ghci/README.md` 参照。
- ⚠ `instance Monad` は書かない（決定事項 2）。ここは
  「型クラスが付く先には 2 種類ある」ことを示すだけで閉じる。

### 8. deriving の正体

- 02 回でずっと使ってきた `deriving` は、**インスタンス定義の自動生成**だった。
- 自分で書いた `instance Show Color` と `deriving Show` を並べて、同じものだと見せる。
  （練習問題と同じ題材になるので、本文では片方を軽く見せて練習に回す配分にする。）
  → 執筆時に本文は `deriving Show` 側だけを載せ、手書きは【問3】に回した。
- `deriving` できるのが標準の 6 種類なのは、
  **構造から機械的に決まる実装しかないから**、という理由づけを与える。
- ⚠ 言語拡張（`DeriveFunctor`・`GeneralizedNewtypeDeriving` など）は**落とす**
  （決定事項 9）。`DeriveFunctor` は 16 回（Free モナド）で動機が立ってから導入する。

### 9. 仕組み: 辞書渡し（**本文に入れる**、決定事項 10）

- ad hoc 多相が実行時に何をしているのか、という答え。
  制約 `Eq a =>` は、コンパイラが**メソッドの実装をまとめたレコード（辞書）を
  隠れ引数として渡す**ことで実現されている。

  ```hs
  -- class → メソッドをまとめたレコード型
  data EqDict a = EqDict { eqMethod :: a -> a -> Bool }

  -- instance → そのレコードの値
  dEqInt :: EqDict Int
  dEqInt = EqDict primEqInt

  -- 制約 (Eq a =>) → 隠れた引数
  f :: EqDict a -> a -> a -> String
  ```

- **要点は「`=>` の左側は、実行時には `->` の引数になっている」の 1 行**。
- これが分かると、構成案 5 で見た 2 つの現象が同じ理由から出てくることが分かる。
  1. **戻り値の型だけで実装が選べる**理由 — 選ぶ材料は値ではなく型なので、
     引数に `a` が現れる必要がない。
  2. **ambiguous エラーになる**理由 — 渡すべき辞書が決まらないから。
     「曖昧」の正体が「どの辞書を渡せばいいか分からない」ことだとはっきりする。
- OO との違いもここで締まる。OO はオブジェクト自身が vtable を持ち歩く
  （値に実装が貼り付いている）が、Haskell は辞書が独立した引数なので、
  値がなくても型さえ決まれば実装が選べる。
- スーパークラスは辞書が辞書を含む形になる（`Ord` の辞書が `Eq` の辞書を持つ）
  ことに 1 行触れると構成案 6 も締まる。
- ⚠ **意味論としての説明であることを断る。** 実際の GHC は最適化で辞書渡しを消す
  （特殊化して直接呼び出しにする）ことが多い。生成コードが常にこの形とは限らない。
- **分量は短く。** specialization・INLINE・辞書の共有には踏み込まない。
  飛ばしても記事が閉じる形にする。

## 決定事項

**覆す場合は理由を確認してから。**

1. **ゴールは「ad hoc 多相という考え方」。** 「モナドを定義できる」ではない。
2. **自作モナドはシリーズを通して対象外。** `instance Monad` を書かせる回は設けない。
   13 回の `Cont` の `instance` 回収も行わない。
3. **パラメトリック多相との対比を明確に扱う。** 冒頭で対比して入り、まとめで回収する。
   型変数自体は既習なので、`=>` の有無が分かれ目という形にする。
4. **`class`/`instance` の入口はオーバーロード。** 02 回の宿題（`:393`）の直接の回収。
   他言語との比較は既存記事に譲る。
5. **`Monoid` はスーパークラスの題材にする。** 09 回の `Writer` の `Monoid` 制約（`:851`）を
   ここで回収する。`mempty` が構成案 5 の例も兼ねる。
6. **`return` と `pure` の関係、`Functor`/`Applicative` は 15 回へ全部送る。**
   14 回では `pure` という名前を出さない。`Monad` の階層も扱わない。
7. **種（kind）は語を与えて `:k` まで見せる。** ただし `instance Monad` は書かない。
8. **`MonadFail` は落とす。** 型クラスの仕組みとして新しいことがなく、経緯の説明に
   分量を取られる。15 回への引き継ぎ事項に書き残す。
9. **`deriving` の言語拡張は落とす。** `DeriveFunctor` は 16 回（Free モナド）で
   動機が立ってから導入する方が自然。
10. **辞書渡しは本文に入れる。** 末尾の独立節、飛ばしても読める形。
    「`=>` の左側が実行時の引数になる」が要点で、実装の詳細には踏み込まない。

### メソッドではない制約付き関数の実例を挙げる

構成案 4（型クラス制約）の導入は自作の `same :: Eq a => a -> a -> String` から入っている。
ここに「実際によく使う関数にも制約が付いている」実例を並べる案を検討したが、
**話題が錯綜するため見送った**。`same` は「制約を書くと中で `==` が使える」という因果が
最短で見える教材で、実例を並べると中身が見えない分だけ説明が増える。

以下は候補として GHCi（GHC 9.6.6）で型を確認したもの。いずれも**型クラスのメソッドではない**
（制約付きの普通の関数）。将来この節を膨らませる場合や、15 回以降で同種の説明が要る場合に使う。

| 関数 | 型 | 備考 |
|---|---|---|
| `print` | `Show a => a -> IO ()` | `Show` のメソッドは `showsPrec`・`show`・`showList` |
| `read` | `Read a => String -> a` | `Read` のメソッドは `readsPrec`・`readList`・`readPrec`・`readListPrec` |
| `lookup` | `Eq a => a -> [(a, b)] -> Maybe b` | 構図が `same` と同じ（中で `==` を使う）|
| `elem` | `(Foldable t, Eq a) => a -> t a -> Bool` | `Foldable` が入るので入門向けではない |
| `nub` | `Eq a => [a] -> [a]` | `Data.List` |
| `sort` | `Ord a => [a] -> [a]` | `Data.List` |

採用するなら `print` が最有力だった。記事中で最初から使い倒していて読者に既知であり、
**`show` はメソッド・`print` は制約付きの普通の関数**という対比がそのまま
「メソッドと制約付き関数は別物」の説明になる。`print` の実装（`putStrLn . show`）が
制約のおかげで `show` を呼べている、という繋ぎ方もできる。

関連: 冒頭（構成案 1）で `show` を「関数」と呼んでいるが、正確には `Show` のメソッド。
メソッドという語の導入は構成案 2 なので、冒頭では「関数」のままにしてある。
構成案 2 で `show` に言及して結び付ける案も試したが、そこは `Foo` の説明に集中させたいため戻した。

### 単相性制限（monomorphism restriction）

構成案 4 に「型注釈を省略しても制約は推論で付く」という `:::message` を入れた
（`same` の直後）。そこで**あえて触れなかった例外**が単相性制限。

引数を書かない定義（単純パターン束縛）では制約が一般化されず、デフォルト規則で
具体的な型に固定される。GHCi（GHC 9.6.6）で確認した。

```
same x y = if x == y then "同じ" else "違う"   -- Eq a => a -> a -> String
plus x y = x + y                               -- Num a => a -> a -> a
plus = (+)                                     -- Integer -> Integer -> Integer
```

同じ意味の定義でも書き方で型が変わるため、説明すると分量が要る。
「数値リテラルだけ注釈が要らない理由」（型のデフォルト規則）の節と地続きだが、
**14 回では扱わない**。

## 記事の狙い

**bind は継続を抽象化したものである**という一点を伝える。
継続モナドは「難しいモナド」ではなく、これまでの回で書いてきた `>>=` の正体を
明示的に取り出したものだ、という位置付けにする。

その上で、応用としてコルーチンを実装して見せる。
「継続が値として取り出せると何が嬉しいか」を、実際に動くものの形で示す。

嬉しさが伝わる地点は**リストで書けないところ**なので、生産専用のジェネレーターで
止めずに、双方向・IO 交互・消費側まで進む。ここが Zenn の単発記事との差分になる
（あちらは「型が循環する」現象とその解消が主題で、リストとの比較で終わっている）。

## 構成案

1. **bind と継続**
   - `m >>= k` の `k` は「残りの計算」＝継続である。
   - `do` ブロックが継続の連鎖に脱糖される様子を、既習のモナド（IO、Maybe、リスト）で確認する。
   - 継続が `>>=` の中に隠れていることを見せる。
2. **継続モナド**
   - **CPS 変換に触れる。** 「戻り値を返す」代わりに「続きの処理を引数で受け取って呼ぶ」
     書き方（継続渡しスタイル）へ機械的に書き換えられることを、小さな例で見せる。
     ```hs
     add  x y   = x + y          -- 直接スタイル
     addK x y k = k (x + y)      -- CPS
     ```
     `(a -> r) -> r` という型がどこから来たのかは、ここを踏んでおかないと唐突になる。
     `Cont` は**この `k` を受け取る関数を `newtype` で包んだだけ**、という順序で導入する。
   - 末尾再帰化の文脈（`cps-to-continuation` の 01・02 回）には深入りしない。
     あちらは「ループにするための CPS」、本記事は「継続を値として掴むための CPS」なので、
     動機が違う旨を一言添えてリンクで済ませる。
   - `newtype Cont r a = Cont { runCont :: (a -> r) -> r }`
   - 隠れていた継続を、そのまま値として保持する型だと説明する。
   - `return` / `>>=` / `evalCont` を実装し、恒等モナドとの対比で「何が増えたか」を示す。
     `>>=` の実装が CPS の関数合成そのものであることを、1 の「継続は `>>=` に隠れている」
     と突き合わせて確認する。
   - 答えの型 `r` の役割を説明する（ここが後のコルーチンの伏線になる）。
3. **callCC**
   - `callCC :: ((a -> Cont r b) -> Cont r a) -> Cont r a`
   - 早期脱出の例（`when (x == 0) (ret "zero")`）から入る。
   - 「現在の継続を引数として受け取る」の意味を、`\x -> Cont $ \_ -> c x` の実装から読み解く。
4. **応用: コルーチン**
   - 継続を返して抜け、後で再開する ＝ ジェネレーター。
   - 答えの型 `r` を自分自身にする必要があること、そこで型が循環すること。
   - **`data` で包んで解決する。** ここが記事の山場。
   - 有限・無限の両方の例を出し、`mapM_` など既存のコンビネーターがそのまま使えることを見せる。
5. **リストとの境界**
   - ここまでの使用例はすべて遅延リストで書ける。
     `[1,2,3]` / `[0 ..]` / `map (^ 2) [1 .. 5]`、一般の状態機械は `unfoldr`
     （`Just (値, 次の状態)` が `yield` に相当）。
   - 遅延評価は「消費されるまで計算しない」ので、`toList` で取り出す形の
     ジェネレーターと役割が重なる。`toList` で `Gen a` → `[a]` に変換できたのは、
     4 のジェネレーターが**生産する側だけ**のコルーチンだったから。
   - ここで止めると「リストで十分」で終わってしまうので、**リストでは表せない側に
     進むための線引き**として置く。境界は次の 3 つ（6 で実装する）。
6. **リストで表せないものを実装する**（本記事独自の見せ場）
   - **(a) 双方向のやり取り** — 再開時に値を渡す（JS の `it.next(x)` に相当）。
     出力の型と入力の型を分ける。`yield` の戻り値が、次の再開時に渡された値になる。
     ```hs
     data Gen i o = Done | Yield o (i -> Cont (Gen i o) (Gen i o))
     ```
     捕まえた継続 `next` は関数なので引数を渡せる、という 3 の `callCC` の話が効く。
     題材は累算器（渡した値を足し込んで途中結果を `yield` する）程度で十分。
   - **(b) 副作用と交互に進む** — 各 `yield` の間で IO を実行する。
     `ContT r IO` に持ち上げる。ここで初めてモナド変換子が必要になる理由を示す
     （純粋なリストでは「出す」タイミングと IO の順序を結び付けられない）。
     題材は `yield` ごとに `putStrLn` する、あるいは 1 行読んで `yield` する。
   - **(c) 入力を消費する側のコルーチン** — 「値を待つ」方向の中断。
     `yield` の双対として `await` を作り、簡単なパーサー（トークンを 1 つ受け取る）を書く。
     生産側と消費側を繋げると pipes・conduit の原型になる、という位置付けで締める。
   - 3 つ全部を厚く書くと長くなるので、**(a) を本編、(b)(c) は短く**が基本線。
     分量次第で (c) を別記事に切り出すことも検討する。
7. **練習**
   - 早期脱出を使う関数を `callCC` で書き換える。
   - `toList` の逆（リストからジェネレーターを作る）。
   - (a) の双方向ジェネレーターを使って、状態を持つ処理を書く。
   - 解答例は `13a-*.md` として別記事にする（シリーズの慣例に従う）。

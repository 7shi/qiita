## 記事の狙い

**bind は継続を抽象化したものである**という一点を伝える。
継続モナドは「難しいモナド」ではなく、これまでの回で書いてきた `>>=` の正体を
明示的に取り出したものだ、という位置付けにする。

その上で、応用としてコルーチンを実装して見せる。
「継続が値として取り出せると何が嬉しいか」を、実際に動くものの形で示す。

嬉しさが伝わる地点は**リストで書けないところ**なので、生産専用のジェネレーターで
止めずに、双方向・IO 交互・消費側まで進む。ここが Zenn の単発記事との差分になる
（あちらは「型が循環する」現象とその解消が主題で、リストとの比較で終わっている）。

**本線はジェネレーター**とする。CPS で継続を取り出して何ができるかの例として最も素直で、
**値を相互にやり取りできればリストを超えられる**という形で「継続が値であること」の
必然性が出る。実用上は既存のジェネレーターやライブラリを使うべきだが、
本シリーズは**実用より原理の理解を優先**する方針なので、自分で組むところを見せる。

ただし実用を無視はしない。**リソース管理（`with` のネスト解消）は必要**なので、
原理を通した後に実用面の回収として置く（構成案 7）。

## 構成案

1. **bind と継続**
   - `m >>= k` の `k` は「残りの計算」＝継続である。
   - `do` ブロックが継続の連鎖に脱糖される様子を、既習のモナド（IO、Maybe、リスト）で確認する。
   - 継続が `>>=` の中に隠れていることを見せる。
2. **継続モナド**
   - **CPS 変換に触れる。** 「戻り値を返す」代わりに「続きの処理を引数で受け取って呼ぶ」
     書き方（継続渡しスタイル）へ機械的に書き換えられることを、小さな例で見せる。
     ```hs
     add  x y   = x + y          -- 直接スタイル
     addK x y k = k (x + y)      -- CPS
     ```
     `(a -> r) -> r` という型がどこから来たのかは、ここを踏んでおかないと唐突になる。
     `Cont` は**この `k` を受け取る関数を `newtype` で包んだだけ**、という順序で導入する。
   - 末尾再帰化の文脈（`cps-to-continuation` の 01・02 回）には深入りしない。
     あちらは「ループにするための CPS」、本記事は「継続を値として掴むための CPS」なので、
     動機が違う旨を一言添えてリンクで済ませる。
   - `newtype Cont r a = Cont { runCont :: (a -> r) -> r }`
   - 隠れていた継続を、そのまま値として保持する型だと説明する。
   - `return` / `>>=` / `evalCont` を実装し、恒等モナドとの対比で「何が増えたか」を示す。
     `>>=` の実装が CPS の関数合成そのものであることを、1 の「継続は `>>=` に隠れている」
     と突き合わせて確認する。
   - 答えの型 `r` の役割を説明する（ここが後のコルーチンの伏線になる）。
   - **`r` の役割の答えの一つが「区切り」。** ここで限定継続に一言触れる
     （下の「限定継続との関係」節。**検証済み**: [check/cont-delimited/README.md](check/cont-delimited/README.md)）。
3. **callCC**
   - `callCC :: ((a -> Cont r b) -> Cont r a) -> Cont r a`
   - 早期脱出の例（`when (x == 0) (ret "zero")`）から入る。
   - 「現在の継続を引数として受け取る」の意味を、`\x -> Cont $ \_ -> c x` の実装から読み解く。
   - **`b` が多相なのは「呼んだら戻らない」ため**（abortive）。これは 6 (c) を落とす際にも、
     `Pipe` で脱出継続を多相に付け直す小細工の根拠にもなっていた性質。
4. **応用: コルーチン**
   - 継続を返して抜け、後で再開する ＝ ジェネレーター。
   - 答えの型 `r` を自分自身にする必要があること、そこで型が循環すること。
   - **`data` で包んで解決する。** ここが記事の山場。
   - 有限・無限の両方の例を出し、`mapM_` など既存のコンビネーターがそのまま使えることを見せる。
5. **リストとの境界**
   - ここまでの使用例はすべて遅延リストで書ける。
     `[1,2,3]` / `[0 ..]` / `map (^ 2) [1 .. 5]`、一般の状態機械は `unfoldr`
     （`Just (値, 次の状態)` が `yield` に相当）。
   - 遅延評価は「消費されるまで計算しない」ので、`toList` で取り出す形の
     ジェネレーターと役割が重なる。`toList` で `Gen a` → `[a]` に変換できたのは、
     4 のジェネレーターが**生産する側だけ**のコルーチンだったから。
   - ここで止めると「リストで十分」で終わってしまうので、**リストでは表せない側に
     進むための線引き**として置く。境界は次の 3 つ（6 で実装する）。
   - **歴史的な補足を差せる（下の「Haskell 1.0 の I/O」節）。** この「リスト vs 継続」は
     Haskell が実際に IO モナドを導入する前に選択した対立軸そのものだった。
     読者に「なぜこの対立が重要なのか」の外部的な根拠を与えられる。
6. **リストで表せないものを実装する**（本記事独自の見せ場）
   - **(a) 双方向のやり取り** — 再開時に値を渡す（JS の `it.next(x)` に相当）。
     出力の型と入力の型を分ける。`yield` の戻り値が、次の再開時に渡された値になる。
     ```hs
     data Gen i o = Done | Yield o (i -> Cont (Gen i o) (Gen i o))
     ```
     **この型のまま通ることを検証済み**（型の循環は再発しない。`RankNTypes` も不要）。
     捕まえた継続 `next` は関数なので引数を渡せる、という 3 の `callCC` の話が効く。
     題材は累算器（渡した値を足し込んで途中結果を `yield` する）程度で十分。
   - **生産専用版からの差分は `(next ())` → `next` だけ。** ここが最大の見せ場。
     ```hs
     yield ccOut v = callCC $ \next -> ccOut (Yield v (next ()))  -- 生産専用
     yield ccOut v = callCC $ \next -> ccOut (Yield v  next    )  -- 双方向
     ```
     生産専用版は捕まえた継続に `()` を渡して潰していただけで、渡さずそのまま
     格納すれば双方向になる。「継続は関数である」が差分そのものとして目に見える。
     `yield` の型が `GenM i o ()` → `GenM i o i` に変わり、脱出継続の答えの型も
     連動して `()` → `i` になる（`callCC` の型から追える）。
   - **`toList` が書けなくなることを 5 の回収として見せる。** `Gen i o` は `[o]` に
     変換できず、入力列を与える `feed :: Gen i o -> [i] -> [o]` になる。
     これが「リストを超えた」ことの証拠。生産専用版で `toList` が書けたのは
     入力が `()` に潰れていたからだと振り返れる。
   - 実行結果を載せるときの注意: ジェネレーターは「まず出して、それから受け取る」ので
     入出力の個数がずれる。`accum` に `[1,2,3,4]` を渡すと `[0,1,3,6]` で、
     `6+4=10` は出ない。一言説明しないと読者が数え違える。
   - 検証コード・確認内容: [check/gen-bidirectional/README.md](check/gen-bidirectional/README.md)
     （標準の `Cont` 版と全部自前の最小実装版の両方。コルーチン部分は `diff` で同一）
   - **(b) 副作用と交互に進む** — 各 `yield` の間で IO を実行する。
     `ContT r IO` に持ち上げる。ここで初めてモナド変換子が必要になる理由を示す
     （純粋なリストでは「出す」タイミングと IO の順序を結び付けられない）。
     題材は `yield` ごとに `putStrLn` する、あるいは 1 行読んで `yield` する。
   - **持ち上げの差分は機械的で、`yield` の定義は 1 文字も変わらない**（検証済み）。
     `Cont` → `ContT ... IO`、`evalCont` → `evalContT`、`runGen` の結果が
     `IO (Gen a)` になる、生産側で `liftIO` を使う。それだけ。
     「`StateT` と同じ要領」で足りることが確認できたので、ここは短く済ませられる。
   - **遅延がなくなることを 5 と対にして書く。ここが (b) の本当の見せ場。**
     純粋版の `take 5 (toList nats)` は遅延のおかげで動いたが、`ContT r IO` では
     `toList` が `IO [a]` になるので効かず、打ち切るドライバーを自分で書く必要がある。
     さらに素朴に書くと**1 つ余分に生産される**（判断する前に再開してしまう）。
     再開の前に打ち切りを判定すれば直る。5 で「遅延評価は消費されるまで計算しない」と
     言ったことの裏返しが、副作用を付けた瞬間に目に見える形で出る。
   - **(a) と組み合わせると「出力を見てから次の入力を IO で決める」ループが書ける**
     （検証済み）。リストでは遅延しても書けないので、(a) 単独より
     「リストを超えた」ことが分かりやすい。(b) は短くする方針だが、
     この例を (a) の締めに置く構成も検討する。
   - 検証コード・確認内容: [check/gen-io/README.md](check/gen-io/README.md)
   - ~~**(c) 入力を消費する側のコルーチン**~~ — **検証の結果、落とした**（下記）。
     **境界は (a)(b) の 2 つとする。** (a) を本編、(b) は短く、が基本線。
     (a) は記事全体の山でもある。「値を相互にやり取りできればリストを超えられる」が
     継続を値として取り出す必然性そのものなので、ここに一番紙幅を割く。
   - **(c) を落とした理由**（検証記録: [check/gen-await/README.md](check/gen-await/README.md)）
     1. **`await` は (a) の部分集合。** 消費側 `Sink i r` は双方向ジェネレーター
        `Gen i o` の出力を潰した `o = ()` の場合でしかない。「継続は関数だから
        引数を渡せる」を (a) で見せた時点で消費側は示せており、新しい概念がない。
     2. **パーサーは 12 回の劣化版。** `Sink i r` を `feed` で駆動するのは
        `StateT [i] Maybe r` と同型で、12 回の `StateT` + `Either` そのもの。
        しかも `await` は消費してしまうので**先読みを自前で持ち回る**必要があり、
        `try` によるバックトラックも書けない（一方向にしか進めない）。
        12 回で説明済みのものを、機能を減らして再掲することになる。
     3. **pipes の原型だけが (a)(b) に無い話だが、そこが一番重い。**
        `yield` と `await` を 1 つの型に統合すると脱出継続の答えの型が固定できず
        `RankNTypes` が要る。さらに `callCC` がくれる脱出継続は単相なので、
        「呼んだら戻らない」ことを使って多相に付け直す小細工（`escape`）も要る。
        **本線（bind は継続の抽象化）から最も遠いところに一番コストがかかる。**
   - 残すとすれば**「消費側は出力を `()` に潰したものなので (a) に含まれる」の一文**だけ。
     5 で `toList` が書けた理由（入力が `()` に潰れていた）とちょうど対になるので、
     (a) の締めに 1 行入れる余地はある。
7. **実用: リソース管理**（`with` のネスト解消）
   - **位置は本線（4〜6）の後**。ジェネレーターで原理を通した後、
     「実際に `ContT` が使われているのはここ」として実用面を回収する節にする。
     世間で `ContT` が使われる用途としてはこれが一番多く、Python の `with` に相当する。
     ここを本線より前に出すと、原理の理解より実用が先に立って狙いがぶれるので出さない。
   - 入口は型の一致。`withFile path mode` を部分適用すると `(Handle -> IO r) -> IO r` で、
     これは `ContT r IO Handle` の中身そのもの。構成案 2 の `(a -> r) -> r` が
     標準ライブラリに既にあった、という形で回収できる。
     `ContT` は 6 (b) で既に出しているので、変換子版から入ることの引っかかりもない。
   - ネストが平坦になることを対比で見せる。
     ```hs
     -- ネスト
     withFile src ReadMode $ \hSrc ->
         withFile dest WriteMode $ \hDest -> ...

     -- ContT
     hSrc  <- ContT $ withFile src  ReadMode
     hDest <- ContT $ withFile dest WriteMode
     ```
     `with` を増やしても縦に伸びるだけで右にずれない、が要点。
   - `evalContT`（`= flip runContT return`）で締める。答えの型 `r` は多相のままにしておく。
   - 解放は取得の逆順（LIFO）で、ネスト版と完全に同じ順序になる。**検証済み**。
   - **遅延 IO の罠**に一言触れる。`hGetContents` の結果を `ContT` の外へ持ち出すと
     閉じたハンドルを読んで例外になる。`with` 系共通の話だが、`ContT` では
     リソースの寿命が `do` の見た目から消えるので踏みやすい。
   - `callCC` で途中脱出しても後片付けは走る（構成案 3 の回収になる）。**検証済み**。
   - `bracket` は 11 回で未出（`grep` で0件）。`withFile` から入るか、
     `bracket_` で自作の疑似リソースを見せるかは要判断。
   - **分量は短く。** 実用の紹介が目的なので、`copyFile` 程度の一例と注意点で足りる。
     深追いすると本線が薄まる。

## Haskell 1.0 の I/O（歴史的補足）

**IO モナド導入前の Haskell は遅延ストリームで副作用を扱っていた。**
この記事の「リスト vs 継続」という対立軸は、Haskell が実際に通った道そのもの。

**歴史そのものは単発記事へ分離した。本編では深入りせず要点だけ参照する。**

- 記事: [Haskell の IO モナドへの道](https://zenn.dev/7shi/articles/20260731-haskell-io-history)（Zenn）
- 検証コード: zenn リポジトリ `check/20260731-haskell-io-history/`

典拠は Hudak, Hughes, Peyton Jones, Wadler,
[*A History of Haskell: Being Lazy with Class*](https://www.microsoft.com/en-us/research/publication/a-history-of-haskell-being-lazy-with-class/)
(HOPL III, 2007) の 7 節。詳細は分離した記事にあるので、以下は本編で使う分だけ残す。

### 前提となる事実（詳細は分離記事）

- Haskell 1.0 (1990) はストリーム版と継続版の I/O を両方載せていた。
  ストリームを primitive、継続をその上の派生とした（理由は効率）。
  モナド版は Haskell 1.3 (1996) で両者を置き換えた。
- プログラムの型は `type Behaviour = [Response] -> [Request]`。
  順序の正しさは遅延パターン `~` で守るしかなかった。

### 本編にとっての価値（検証で分かったこと）

1. **答えの型 `r` の具体例が歴史上にある。** Haskell 1.0 の継続 I/O では
   `readFile name abort :: (String -> Behaviour) -> Behaviour` で、これは
   `Cont Behaviour String` そのもの。`r` が「これから OS に出す要求の列」という
   具体物だった。構成案 2 で「`r` は抽象的で掴みにくい」と言った後の実例になる。
   実際に `Cont` で包んで `do` 記法にしたら Figure 6（モナド版）と同形になった。
2. **双方向ジェネレーターは `Behaviour` そのもの。** 構成案 6 (a) の
   `feed prog :: [Response] -> [Request]` が型として `Behaviour` に一致する。
   Figure 3 のプログラムをコルーチンとして書いて Haskell 1.0 の OS に差したら動いた。
   `[Response] -> [Request]` は**双方向コルーチンを 2 本の遅延リストで表したもの**だった。
3. **`~`（遅延パターン）の必要性が、こちらの落とし穴と同じもの。**
   `~` を外すと Figure 3 はデッドロックする。そして `gen-bidirectional` の
   `feed`（入力を先にパターンマッチする版）を knot-tying で使うと**同じくデッドロックした**。
   出力を先に出す形に直すと通る。つまり `~` でやっていた配慮が、コルーチンでは
   ドライバー側に移り、プログラム本体では意識せずに済む。
   `gen-io` の「素朴な `take` が 1 つ余分に生産する」も同じ型の同期のずれ。
   **純粋なら遅延が吸収するが、副作用が付くと露出する**という一点に集約される。

### 構成上の扱い

- **分量は数行に抑え、詳細は分離記事へのリンクで済ませる。**
  `Behaviour` の型と「`~` が必要だった」「継続版もあった」の 3 点程度。
  Figure 3・4 を載せる必要はない（分離記事にある）。
- 記事全体の狙い（**bind は継続を抽象化したもの**）とも噛み合う。論文が
  「Haskell を命令型っぽく見せたのはモナドそれ自体ではなく `do` 記法の登場だった」
  と書いており、構成案 1 の「`do` は継続の連鎖に脱糖される」と直結する。
- **要判断（残る判断 1）**: **5 と 6 の間**か **6 (a) の後**か。
  前者は 5 で「リストで十分では」と言った直後に「実際に Haskell はリストを選び、
  後で捨てた」と繋げて 6 への動機を強める。後者は型の一致
  （`feed prog` = `Behaviour`）を見せて「今書いたものが Haskell 1.0 だった」と落とす。

## 限定継続との関係

**「継続モナドは真のコールスタックをいじらないので、限定継続では？」への答え。**
**検証済み**: [check/cont-delimited/README.md](check/cont-delimited/README.md)

争点を 2 つに分けると整理できる。**到達範囲としては限定的だが、`shift`/`reset` とは別物。**

1. **捕まえた継続は first class**（ここは限定的ではない）。ただの関数値なので
   データ構造に格納でき、`evalCont` が返った後でも、何度でも呼べる（`GenClone.hs`）。
   **「コールスタックをいじらない」ことは first class 性を損なう理由ではなく、
   成り立たせている理由。** Scheme のネイティブ `call/cc` がスタックのコピーで達成する
   multi-shot を、CPS では継続がクロージャなのでタダで得ている。
2. **到達範囲は `evalCont` まで**（ここは限定的）。脱出しても `evalCont` の外は実行される。
   **答えの型 `r` が区切り（prompt）の正体**と言える。
3. **`callCC` は abortive、`shift` は composable。** ここが決定的な差。
   `callCC` の `k :: a -> Cont r b` は `b` が多相＝戻らないので、`x <- k 1` の後は
   到達しない。`shift` の `k` は値を返すので `k (k 3)` や `k 10 + k 20` が書ける
   （`reset (1 + shift (\k -> k (k 3)))` = `5` がそのまま動く）。
   `reset`/`shift` は自作不要で `Control.Monad.Trans.Cont` に入っている。

→ **`callCC` は「区切りの中の undelimited な call/cc」。**
「セマンティクスとしては限定継続」は、到達範囲の話としては正しく、
継続の性質の話としてはミスリード。

### 構成上の扱い

- **触れる**（残る判断 3 で決定）。Scheme の 2 部シリーズを読んだ読者は
  「Haskell の `callCC` は Scheme の `call/cc` と同じか」を必ず思うので、放置すると宙に浮く。
- **深入りはしない。** 上の 2 と 3 の 2 点＋ Scheme 2 部シリーズへのリンクで足りる。
- **置き場所は構成案 2 の「答えの型 `r` の役割」。** `r` が何かという問いの答えの一つが
  「区切り」なので、PLAN が「`r` は抽象的で掴みにくい」と書いていた部分の回収になり、
  伏線の張り方としても噛み合う。

## 他言語との対応（async/await・with）

**Node.js の `readFile` がコールバックを取るのは継続渡しで、async/await はその抽象化。**
読者の多くが async/await を知っているので、**継続モナドの入口として使える**。

### ⚠ 既存記事が既に書いている

**[非同期APIをPromiseでラップしてasync/awaitで使う](https://qiita.com/7shi/items/a2bb35f27cd4a56f7bac)
（`articles/javascript/wrap-async-api-with-promise.md`, 2020）が JS 側をほぼ全部覆っている。**
コールバック地獄 → Promise → async/await → `co`（ジェネレーター版）まで揃っていて、
コールバックを CPS と呼び、`resolve` が継続に近いことにも触れている。まとめには
「コールバックから async/await への書き換えは、Haskell での `>>=` を明示した書き方から
do ブロックへの書き換えに対応します」と書かれ、本シリーズ 05 回にリンクしている。

同記事が挙げる `resolve` と継続の相違点は、そのまま使える材料。

- 継続は後続を打ち切るが、`resolve` は後続を実行してから非同期で `await` に戻る。
- **継続は何度でも呼べるが、`resolve` は 2 回目以降何も起きない。**

後者は下の「既存のジェネレーターより能力が上」と直結する。

### 新記事だけが言えること: 既存のジェネレーターより能力が上

**`Gen i o` は純粋な値なので、同じ中断点から何度でも再開できる**（検証済み、
`check/gen-bidirectional/GenClone.hs`）。違う入力で再開すれば分岐して木になる。

```hs
let g = step accum 10
peek (step g 1)     -- Just 11
peek (step g 100)   -- Just 110   ← g は消費されない
```

JavaScript / Python のジェネレーターはこれができない（だから
「イテレーターのクローンもどき」が最初からやり直す回避策を書いている）。
Promise も `resolve` を 2 回呼べない。

→ **「実用には既存のジェネレーターを使えばよいのでは」への答えになる。**
原理を理解するために自前で組む、という方針（記事の狙い）に加えて、
**自前版の方が能力が上**という実利まで言える。`callCC` の
「継続は何度でも呼べる」がそのまま機能として出ている点で、構成案 3 の回収にもなる。

### 補足: コールバック段階と継続モナドの対応

姉妹編 `cps-to-continuation` の 03 回は Promise（`then` = bind、`async function` = do）に
触れているが、**コールバックを `Cont` で包む段階は未出**。そこだけは新記事で書く価値がある
（下記 2 が Haskell 1.0 と直結するため）。

### 使える対応

1. **コールバックを部分適用すると `(a -> r) -> r`。**
   ```js
   const readFileK = path => cb => fs.readFile(path, 'utf8', cb);
   ```
   構成案 7 の `withFile path mode :: (Handle -> IO r) -> IO r` と同じ形。
   **`with` 系と Node のコールバックは同じもの**だと言える。
2. **Node の `(err, data)` は Haskell 1.0 の 2 継続を 1 つに畳んだもの。**
   分けて書くと `readFile :: Name -> FailCont -> StrCont -> Behaviour` に一致し、
   失敗継続を固定すると `Cont` になるところまで同じ（一対一で対応することを確認済み）。
   **Haskell 1.0 の I/O モデルは実質 Node のコールバック API だった。**
3. **callback hell = Figure 4 の括弧の山。** 同じ問題が 1990 年と 2010 年代に別々に起き、
   どちらも同じ方向（`do` 記法 / async-await）で解決された。
4. **双方向ジェネレーター + ドライバー = async/await の実装方式**（`co`・regenerator）。
   ここが一番強い。`it.next(value)` が構成案 6 (a) の双方向 `yield` そのもので、
   ドライバーは `gen-io` の `drive` と同じ形。**6 (a) + (b) を組み合わせたものが
   async/await だった**と言える。JS 版と async/await 版で出力が一致することを確認した。
5. **Python の `with` はジェネレーターで実装できる**（`@contextmanager`）。
   `yield` の位置で `with` の本体（＝継続）が走る。手で駆動すると
   `with_` が `runContT`、`body` が継続だと露わになる。出力は
   `cont-resource/Order.hs` と完全に一致した。
   → **構成案 6（コルーチン）と 7（リソース管理）は別の応用ではなく同じ仕組み。**
   Python がそれを実装で実証している。7 を「おまけの実用例」ではなく
   **本線の言い換え**として位置付け直せる。

- **入口（構成案 1 か 2）で async/await に一言触れる**のが有力。「あなたが使っている
  async/await は継続モナドである」から始めれば、`(a -> r) -> r` が唐突でなくなる。
